# 完整 ROM 恢复与诊断

使用同一台机器在原厂系统中备份的、从物理偏移 0 开始的完整 Flash 主数据文件。旧原厂 Web 程序的 `/backup/N` 直接读取 `/dev/mtdN`；如果原厂 `mtd16` 覆盖整片 Flash，它下载的 `.bin` 就是这种输入。256 MiB 的准确字节数是 `268435456`，以设备实际容量为准。

恢复入口只接受大小恰好等于 Flash 主数据容量的文件。包含 OOB 的编程器镜像、跳过坏块后压紧的 `nanddump`、单个分区镜像、sysupgrade，以及本项目的 ZIP/TAR 备份，需要先确认格式和地址映射，不能作为整片 ROM 直接上传。

## 机器正在运行旧版 Web U-Boot

无需先刷入新版。先用 Python 3 从电脑读取现有服务的信息，URL 使用你当前能打开的 Web U-Boot 地址：

```sh
python3 tools/recovery-client.py http://192.168.0.1
```

默认只请求 `/api/device` 和 `/api/task`，打印机型、RAM、Flash、版本和任务状态。旧版页面只显示“请求失败”时，先单独测试上传：

```sh
python3 tools/recovery-client.py http://192.168.0.1 --rom /path/to/mtd16-ROM.bin --upload-only
```

这个模式只把文件上传到 RAM，**不会发送擦除或写入任务**。文件以 64 KiB 分块从电脑发送，不需要在电脑内存中复制整份备份。设备仍需要能容纳完整 ROM 的连续 RAM，这沿用上游逻辑。

成功时会显示 `upload_id`；失败时保留 HTTP 状态码、接口路径和响应正文。新后端还会解释 Flash 容量不符、设备不可用、连续 RAM 分配失败等原因。旧后端可能仍只返回 `invalid request`，此时需要保留真实状态码和请求路径，结合 U-Boot 日志继续定位。GET 请求上传接口得到 404 不能证明 POST 接口不存在。

确认文件来自本机、长度正确且上传接口可用后，可通过现有后端执行恢复：

```sh
python3 tools/recovery-client.py http://192.168.0.1 --rom /path/to/mtd16-ROM.bin --restore
```

程序会显示文件 SHA-256 和覆盖范围，要求在终端输入 `RESTORE`。随后重新上传文件，并且只发送一次 `flash-all` 任务；不会自动重试擦写请求。成功后显示完成，手动重启即可。

如果旧后端没有 `/api/upload-all-flash` 或 `flash-all`，工具无法凭空补齐；需要依据该版本实际接口、串口能力或可用的内存启动镜像另行恢复。不能只凭模糊的 403/404 判断失败原因。

## 新版向导

展开“恢复原厂完整 ROM”，选择文件，勾选属于本机的确认，再点击“上传并恢复”。页面先向设备读取容量和恢复能力，然后复用上游专用整片上传及写入接口。

恢复按原始物理偏移逐块擦除、写入、回读比较。发现已有坏块时保留该物理位置，跳过对应块，不移动后续数据；NAND 驱动生成 ECC。若备份中的有效数据落在目前的坏块上，不能据此保证原厂系统可启动。回读通过只证明写入的数据匹配，不能证明 ROM 内容、厂商 ECC 约定或备份来源正确。

恢复覆盖 BL2、FIP、板级数据和系统，整个过程不能断电。写入失败时不要立即重启；保存出错阶段、偏移和返回码，保持 U-Boot 在 RAM 中运行再处理。页面只在整个任务成功后提供“重启进入原厂系统”按钮。当前恢复功能通过主机模拟测试及交叉编译，尚未实机验证。
